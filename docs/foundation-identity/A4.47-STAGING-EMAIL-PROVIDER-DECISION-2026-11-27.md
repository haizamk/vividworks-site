## 1. Provider comparison (staging)

Comparison uses this repository’s Laravel **13** layout: `config/mail.php`, `config/services.php`, and `.env.example`. Staging today has **no** outbound mail configured (A4.46).

| Criterion | **Resend** | **Amazon SES** | **Standard SMTP** |
|-----------|------------|----------------|-------------------|
| **Laravel 13 compatibility** | Supported in `config/mail.php` (`MAIL_MAILER=resend`). Credential via `RESEND_API_KEY` in `config/services.php`. May require adding the framework’s Resend mail transport dependency during I1 (not present in `composer.json` today). | Supported (`MAIL_MAILER=ses` or `ses-v2`). Uses `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION` (shared pattern with `services.ses`). May require AWS SDK / mail transport packages when implemented. | **Fully supported today** via existing `smtp` mailer block (`MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_SCHEME`). No extra Composer packages for basic SMTP. |
| **Sender domain verification** | Provider dashboard: verify **domain** or single sender; DKIM DNS records on chosen domain/subdomain. | **SES identity verification** (domain or email); DKIM + SPF (and often DMARC) on sending domain. Production exit from sandbox is separate from staging. | Depends on provider (mailbox host, relay, or transactional SMTP). Usually requires verified From domain or allowed relay user. |
| **Staging setup requirements** | Staging-only Resend **API key**; verified staging sending domain/subdomain; `MAIL_MAILER=resend`, `RESEND_API_KEY`, `MAIL_FROM_*`. | Staging-only **IAM user/role** (least privilege `ses:Send*`) in chosen region (e.g. `ap-southeast-1` or `ap-northeast-1` aligned with Supabase staging); verified domain; `MAIL_MAILER=ses` + AWS vars + `MAIL_FROM_*`. | Staging SMTP host/port/credentials in Coolify/host env; `MAIL_MAILER=smtp` + `MAIL_*`; optional `MAIL_SCHEME=tls` (Laravel 13 — not legacy `MAIL_ENCRYPTION`). |
| **Operational complexity** | **Low–medium:** simple API; good fit for transactional mail; fewer moving parts than full AWS. | **Medium–high:** IAM, region, sandbox limits, bounce/complaint handling, DNS. Mature at scale; more ops surface for a small staging footprint. | **Low–medium** if using an existing transactional SMTP; **higher** if self-operated (reputation, TLS certs, relay policy). |
| **Isolation from Production** | **Strong** when using a **separate Resend project/API key** and **separate verified subdomain** (e.g. `staging-mail.*`). No shared API key with production. | **Strong** with **separate AWS account or IAM credentials**, **separate SES configuration set/domain**, and **staging-only From addresses**. Do not reuse production access keys on `vividworks-vm100`. | **Strong** with **dedicated staging SMTP credentials** and **staging-only From domain**; never point staging at production mailbox credentials. |
| **Fit with architecture v1.0.1** | Listed as example transactional path (“Resend/SES”). | Listed as example transactional path. | Explicitly supported; fastest path given current repo (A4.46). |

**Documentation-only recommendation (not an owner decision):** For **staging I1 entry**, **standard SMTP** or **Resend** offer the simplest proof path for **D-EMAIL-V** delivery tests; **SES** is viable but heavier for staging-only unless AWS is already standard for VividWorks mail. Khairul must approve the provider.

### Why `APP_ENV=production` on staging needs an explicit decision (A4.46)

Findings:

- Public endpoint: **`api-staging.vividworks.my`** (staging scope).
- Laravel bootstrap reported **`APP_ENV=production`** on the staging application host.

Why this matters **before I1**:

1. **Operator safety:** logs, alerts, and runbooks may treat the host as production.
2. **Framework behavior:** `production` can affect config caching, error verbosity, and assumed deployment guards.
3. **Verification URL confidence:** signed email links depend on **`APP_URL`**, not `APP_ENV`, but mislabelled env increases risk of copying production env templates onto staging.
4. **Gate discipline:** A4.41 / Gate 5 expect staging mail proof on a **clearly identified staging** stack — env naming is part of that identity.

**Required owner/ops decision (not executed in A4.47):** Approve target values for **`APP_ENV`** and **`APP_URL`** on staging before configuring mail and before the first verification delivery test.
